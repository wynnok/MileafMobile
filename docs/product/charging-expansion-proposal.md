# 充电扩展方案：把每一次补能变成明白账

2026-10-28：用户已确认 A「补能账本」及 CH01–CH05 范围，正式实施见[实施记录](../implementation/charging-briefing.md)。下文 2026-10-27 的“待用户评审”与接口缺口是设计当日的历史状态；0.2.0 实际契约以新冻结文件和服务端增量规格为准。CH06、地图空间聚合及跨会话比较继续后置。

2026-10-27。**待用户评审，尚未实施正式Flutter页面。** 本轮按用户要求只交付产品方案、可交互原型和待补接口说明；不把既有湖畔视觉或先前概览/行程的确认扩大成这次充电扩展的确认。

## 产品判断

建议采用 **A「补能账本」**：先回答这段时间花了多少、补了多少、记录了多久，再从趋势走到地点和单次过程。把 B「时间日历」作为找日期和观察补能节奏的方式，把 C「地点足迹」作为自己的地点档案；三者是同一充电区的不同入口，不增加三个主导航。继续沿用已确认的湖畔主题。

如果我是特斯拉车主，我首先关心的是：**我的日常补能有没有变贵；钱主要花在哪；外出补电够不够快；这一次从多少充到多少，过程有什么变化。** 功率峰值、电压和相数有价值，但应为这些问题服务。一次175kW的峰值不如「18%→82%、34分钟、补入46.8kWh、费用71.28」完整；“夜间充电”也不能自动说明享受了谷电。

这是基于本应用和数据的设计假设，尚未做车主访谈或真人可用性验证。目标是让用户先读懂一个结果，随后能追到时间、地点和记录依据。

## 已核对的当前问题

- `charging_page.dart` 是日期筛选和日期分组的记录列表。每条有地点、两类能量、SOC、费用和时长，但多个字段逐行平铺，没有期间费用、补能节奏或地点上下文。
- `charging_detail.dart` 已有功率/电量曲线、SOC区间、两侧能量、费用、温度和相数。过程可读，但没有原始峰值/时均值、SOC区间用时、电压/电流等输入；工程采样解释占主阅读空间。
- 期间次数、入电量、已知费用/均价与AC/DC能量已在独立统计接口，不必让用户每次切到统计页才能理解眼前记录。完整长区间、多粒度分析仍归统计页，充电主页只保留一个可切指标的紧凑日图。
- **当前列表按 started_at、完成充电统计按 ended_at。** 跨夜会话会落到不同日期；不能直接把统计柱图连到现有开始日列表，再称精确的当天记录。
- TeslaMate的 Charges、Charge Details、Charging Stats 涵盖费用、能量、续航变化、功率、电压、电流、温度和地点等主题。它提供阅读深度的参考；实际输入、缺失和计算仍须逐项核对，不能照面板数量承诺能力。

已读取 GitHub 最新 [Spec #1](https://github.com/wynnok/MileafMobile/issues/1)、[#12「充电历史与币种设置」](https://github.com/wynnok/MileafMobile/issues/12)、[#13「充电详情与功率／电量曲线」](https://github.com/wynnok/MileafMobile/issues/13)、[#15「充电统计与费用／能量口径」](https://github.com/wynnok/MileafMobile/issues/15)。本方案尚未变更这些工单的正式范围、原生依赖或验收状态；确认后增量同步既有票，不重复建票。

## 车主问题、指标与动作

| 层级 / 问题 | 结果与指标 | 呈现与可执行动作 |
| --- | --- | --- |
| 1 这段时间补能花了多少？ | 已知费用、费用记录次数/对应电量、入电均价、总入电量、已完成次数 | 费用主数；覆盖紧邻费用，另列入电量/均价/记录时长。均价不是运营商电价；点击进入相关记录 |
| 1 什么时候补了多少、费用怎样变化？ | 每日入电量、费用、均价、次数 | 单张时间图切指标；纵轴单位随指标变化。点日读数，再明确进入结束日的匹配记录；不画未来日期 |
| 1 哪种方式在支撑我的日常？ | AC/DC/未知入电量、已知分类DC能量占比、各类记录时长 | 同尺度水平条和精确读数；未知独立标明，不把DC都叫Tesla超充，也不把AC都叫家充 |
| 1 钱花在哪些地方？ | 稳定地点分组的次数、入电量、已知费用、入电均价和覆盖 | 按补入电量排序的地点账目；点击地点看该地全部匹配记录。地图是辅助的记忆锚点，排行不按“省钱/快慢”打分 |
| 1 能否找回一次特定充电？ | 日期、地点、AC/DC/未知、费用已知/未知、入电均价/时长排序 | 搜索作用于完整查询集合，匹配总数与摘要随查询变化；游标分页。不能只筛手机上已载入的20条 |
| 2 这一次补得怎样？ | 起止SOC、增加百分点、入电量、已记录费用、记录时长 | 简短结果区 + 0–100%SOC区间；随后立即进入功率曲线。地点和时间用于识别记录，不用记录ID当标题 |
| 2 快充的过程快在哪里、慢在哪里？ | 原始功率峰值、时间加权均值、完整20–80%记录用时、功率/SOC过程 | 曲线按时间或SOC查看；20–80单独注明有效覆盖，未经过两个阈值就不提供确定值。原始峰值与抽样图峰值分别说明 |
| 2 看到下降的功率后，还能查看哪些共同变化？ | 电压、电流、室外温度、加热状态、额定/理想续航过程 | 主图按指标切换；同时间轴读数，不默认双纵轴。加热状态作离散轨道，不能当耗电量；只能观察共时变化，不自动解释因果 |
| 2 电网侧与电池侧有何区别？ | TeslaMate电网侧估算、充入电池量 | 同尺度并列条形，各自完整命名；不相加，不用差值自动命名精确损耗或电池健康 |
| 3 日常如何安排补能？ | 开始小时/星期分布、端点SOC分布、记录时长分布 | 日历和时段分布，结合自己的端点区间。时间分布不是电价分布，不按普适SOC阈值给健康评分 |

不纳入本方案的推断：桩位空闲/排队、未来到站/充满倒计时、桩的额定标称功率、精确电池温度、分时电费/服务费拆分、运营商账单核验、剩余寿命/健康分、把本期充电费分摊成每百公里用车成本。现有数据不能可靠回答这些问题。

## 三种原型的信息结构

原型入口：[操作说明](../prototypes/charging-expansion/README.md)，[图册](../prototypes/charging-expansion/renders/index.html)。原型以固定合成数据演示，不与任何站点连接；评审区可切换「完整方案」和「仅现有冻结接口」。默认展示完整方案，以便先评审产品价值，缺口由评审区和本方案明确列出。

### A「补能账本」：推荐默认

主页：**期间 → 已知费用主数及覆盖 → 入电/均价/记录时长 → 单张每日图 → AC/DC/未知结构 → 地点账目 → 最近记录**。费用是视觉锚点，主图在默认首屏内可读；「全部记录」入口始终可发现，记录视图有独立搜索筛选，不强迫滚过所有分析模块。记录卡将地点、入电量、费用和SOC区间分层，电网侧等次级信息进入单次回顾。

详情：**地点/时间 → 补能结果与SOC → 默认功率曲线 → 原始过程摘要 → 20–80用时 → 两侧能量 → 本次账目 → 车辆与环境 → 原始明细**。完整方案允许在同一绘图区切功率、电量、电压、电流、室外温度和额定续航，以及按时间/SOC读过程；扩展后的加热状态离散轨道、理想续航口径留给接口和正式实现，当前原型未画成已交付控件。

取舍：比旧列表多了期间和地点上下文；首屏仍只有一个主数与一张主图。信息丰富来自逐层展开和可追到记录的联系，而非堆十几张等权卡片。

### B「时间日历」：时间优先

主页：**充电日历 → 所选结束日的记录 → 开始时段与SOC区间 → 期间账目/分类**。有充电的日期用电量读数和类别区分，真实无记录为点、未来日期虚淡且不可点击。夜间只定义为18:00—次日06:00的会话开始时段，不推导谷电比例。

详情：**结果与SOC → 20–80用时 → 过程 → 能量/费用/环境**。强调记录时长，不把它叫排队时间、占桩时长或车主等待。

取舍：找特定一天很直接，但一个月的日历占用较多首屏，费用和地点发现弱于A。建议作为日图的可切阅读方式，而非全局默认。

### C「地点足迹」：地点优先

主页：**期间地点分布 → 地点账目 → 地点内记录 → 期间摘要**。地点数字代表完整期间次数，未知/未定位单列，不凭地址同名合并，不把位移示意画成车辆行驶路线。点地点进入自己的记录和有效费用范围；各地点不被命名为“最佳”“最划算”。

详情：**结果/SOC → 地点锚点和本地历史入口 → 过程 → 本次账目**。

取舍：适合异地/长途补能回顾，但依赖空间聚合和底图条件。当前接口模式只显示已载入记录的地点，并明确「本页」，不冒充全历史地图或地点排行；原型地图为自行绘制的合成示意，正式仍需沿用底图许可、坐标与网络验收。

「现有」表示冻结契约可提供，不代表本轮已经实现页面；新增项均为待评审方案。**本轮只交付方案，不启动以下正式实施顺序。**

| 1 | 期间费用/入电/次数/均价，单张多指标日图；分类绝对值 | 现有 charging stats，直接用totals/buckets；不汇总分页、不平均桶比率 | 现有接口模式的A |

| 2 / P1 | 费用记录覆盖、有效均价分母、记录充电时长、显式未知分类/覆盖 | `charging_processes`已有数据；需新增统计字段及口径，不从当前分页推算 | 完整方案的费用覆盖/时长/未知 |
| 2 / P1 | 全区间找记录、结束日下钻、地点账目 | 需稳定地点标识、统一筛选/time_basis与匹配集汇总、按查询分页和分组端点 | 记录视图、A地点卡、C地点 |
| 3 / P2 | 原始峰值/时均功率、20–80区间用时、采样质量 | `charges.date/charger_power/battery_level`；后端基于原始记录计算并返回有效覆盖与状态 | 完整方案详情 |
| 3 / P2 | 电压/电流/温度/额定或理想续航/加热开关与充电器信息 | `charges`与`charging_processes`已有字段，需新增series/detail与能力声明 | 完整方案前六项曲线；加热轨道/理想续航待正式深化 |
| 4 / P3 | 时段/SOC分布、地点历史趋势、跨会话可比DC曲线 | 需全查询聚合和有效样本规则；同车型/同SOC/同温度等条件可见 | B开始时段/最近SOC区间；其他为候选 |
| 4 / 评估 | 有效配对的两侧能量比 | 同时有效的added/used配对与覆盖；不平均比率，不把used小于added强行夹成100% | 原型先保留两侧原值，不展示效率/损耗率 |

建议先做顺序1，同时补P1；P1可用后才能交付完整的A账本与地点闭环。P2随后加深单次过程，P3按实际使用反馈选取。仅做顺序1会改善层级，但不会解决费用覆盖、完整搜索和地点账目不足，应明确把它称为第一步。

## 数据可信度与异常状态

1. 完成统计默认按结束时间归期，进行中独立显示。完整方案的日图→记录与地点筛选需使用同一`time_basis`和过滤条件；旧列表开始日默认保持，跨夜样例进入后端验收。各资源分别标明查询范围/快照，失败保留成功区块。
2. `cost=null`是未知，`cost=0`是明确零；没记录不是免费。均价分母必须能追溯。现有`cost_per_kwh`直接展示原值，不能在移动端重算；当前SQL的费用分子和非空能量分母在缺能量记录上可能不完全配对。新增有效均价对象以同一批费用已知且能量>0的会话计算，并返回剔除计数；不静默修改旧字段语义。
3. 显示费用覆盖次数、对应入电量，并区分「费用已知」和「均价可计算」。缺能量会话的费用仍属于已知总额，但不能进入有效均价分子。无币种时显示「币种未知」；选择CNY仅加标签，不改数值或换汇。
4. TeslaMate网侧能量是由功率或电压/电流/相数结合时间得到的估算，不是运营商电表。保留两侧原值；未知、零、used<added分别处理，不能取`max(added,used)`掩盖异常，也不直接宣称差值都是损耗。
5. `duration_min`是TeslaMate记录跨度，不是人等待/排队、插枪至拔枪或断电后的占位时长。峰值取原始charges；均值按有效原始相邻时段加权并返回未覆盖时长。不能平均200个采样点或积分手机曲线。
6. 20–80是实际记录的阈值跨度：主例13:13首次有效达到20%，13:41首次有效达到80%，相差28分，不插值；未覆盖两个阈值、无效间隔、回退歧义或进行中，不给确定时长。规则与质量阈值由后端明确，前端展示状态，不宣称标准充电成绩或未来预测。
7. 室外温度不冒充电池包温度；开关状态不等于加热功率。品牌来自原始字段，DC本身不意味着Tesla品牌。额定/理想续航分别命名，不用SOC反推真实电池容量或可达距离。
8. 地点依次使用稳定围栏ID、地址ID；两者均无则归未定位。可保留会话自身坐标但不默认按名字或隐含距离聚类成站点，不做外部逆编码。地图不可用不妨碍地点列表与记录；“家”只是样例已有围栏名，不是方式推断。
9. 列表、期间统计、地点分组、详情、序列各自加载/重试，切车和会话隔离沿既有规则。服务器未支持扩展时隐藏对应专题并说明能力，不以假零图补位。列表区间不因统计730天上限而被强行限制。
10. 费用/电量/次数为0时保留；null留空/断线；真实无记录用空态。浅深色、360px与200%字号检查保留同等内容，图形提供精确读数与无需精细手势的选择方式。

## 样例与原型评审任务

固定时钟：2026-10-27 19:10，Asia/Shanghai。近30日12次已完成，补入358.6kWh；10次有费用，已知费用285.58CNY，对应328.2kWh，入电均价约0.87CNY/kWh；总记录时长37小时30分。AC219.5kWh、DC126.5kWh、未知12.6kWh。零费用会话保留，未知费用不补0。此处CNY是样例已选择的站点标签。

主例：湖畔超级充电站，10/27 13:12–13:46，18%→82%，46.8kWh入电、49.5kWh网侧估算、费用71.28CNY。入电均价约1.52，网侧均价1.44；两个分母分别标明。原始峰值175kW、记录均值87.4kW为独立的合成服务端统计；展示采样最高166kW，不把二者混用。

跨夜例：10/25 23:10–26日03:30，28.6kWh。结束日查看应能找到它，开始日查看仍保留原语义。进行中例60%→进行中、已补2.2kWh，不能进入完成统计或生成最终时长/20–80结果。

请评审以下任务，而不是评价“卡片够不够多”：

- 在10秒内说明本期补入电量、已知费用、费用覆盖，以及均价使用哪类电量。
- 从有充电的一天找到对应会话，验证跨夜不会漏；从地点账目走到该地历史，知道筛选作用于整个区间。
- 在单次回顾前两屏读懂SOC变化、入电、费用、记录时长与功率过程，再区分采样读数和原始统计。
- 在缺失/进行中/局部失败时仍能完成能做的任务；不会把未知当0、把夜间当谷电、把额定续航当预测。

这些是待真人评审的任务，不是已完成的用户研究成绩。浏览器检查与截图记录见原型`renders/verification.md`，不能代替正式Flutter/真机/真实站点验收。
