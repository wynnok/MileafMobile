# 行程扩展方案：从记录列表到出行回顾

2026-10-27。状态：**产品建议与待评审原型，未获准实施正式页面**。本轮按用户要求先出方案、更新原型；不修改 Flutter、冻结契约、后端或已发布 Spec，不更新/关闭 GitHub 工单。沿用已确认的「湖畔」视觉与只读、隐私、外部待验边界。

## 产品判断

「行程」应成为车主回顾自己的出行、理解每趟耗电、再次找到一段路的地方。它需要同时做好**找记录**和**读懂一次出行**。我的建议是以 A「出行回顾」作为默认入口，吸收 B 的能耗参照与过程联动；C 的路线积累作为下一阶段重点。

如果我是车主，我会先问：这几天去了哪里？这趟开了多远、多久，用了多少电，到达还剩多少？这次比自己的日常水平怎样？接着才会关心：变化发生在什么路段，当时的速度、坡度与环境怎样？最高速度、峰值功率有查看价值，但不应抢占路线和电量的位置。

这是一组基于当前产品与数据的**设计假设**，不是已完成车主访谈或可用性研究的结论。原型要验证的是：用户能否迅速找到一趟记录，并在前两屏读懂它，而不是能否放进更多面板。

## 当前问题与证据

- 列表只有日期筛选与同权记录卡片。`energy_kwh` 已在列表 DTO 中，页面却未展示。距离、时长、电耗几乎只有逐行文字；没有期间上下文和可定位日期的出行节奏。
- 详情已有不少数据，但电量区间在长曲线和地图之后；净能量、均速/最高速度、最大功率、内外均温集中在「更多行程指标」。读者需要先读技术采样说明，再找自己关心的结果。
- 当前正式渲染中的「服务端采样」「不是原始极值」等解释占用主阅读空间。口径必须准确，但应把长解释收进帮助层，图旁只留影响判断的短提示。
- TeslaMate 的 Drives / Drive Details / Drive Stats 已覆盖路线筛选、功率与续航、温度/胎压、回收、爬升/下降、速度时长分布、目的地排行等主题。Mileaf API 只开放其中一部分；丰富产品既需要重组已有数据，也需要有顺序地补输入。

已核对 GitHub 当前 #1、#9「[M1-08] 行程筛选与游标分页」、#10「[M1-09] 行程详情与采样图表」，现有验收规则继续有效。这里的新增建议尚未成为这些工单的已确认范围。

## 车主问题决定指标的层级

| 车主问题 | 主结果 | 合适的呈现与动作 |
| --- | --- | --- |
| 最近去了哪里，哪天开了车？ | 期间里程/次数；每日里程；按日分组的起终点 | 紧凑期间摘要 + 一条可点日期的出行节奏图；点日定位记录，返回完整区间 |
| 这趟开了多久、用了多少电？ | 距离、时长、估算净能量、估算净电耗 | 列表直接给能量，详情将四者组成有主次的结果区；能量和电耗分别表示规模与强度 |
| 出发与到达还有多少电？ | 起止 SOC、百分点变化 | 同一 0–100% 电量区间条，起止精确值与「下降 8 个百分点」；不把两端值画成过程曲线 |
| 这个电耗有什么参照？ | 本次与同车此前30个完整日历日的整体净电耗 | 同单位、同尺度并列读数；直接写明「全部路线」与参考区间。此阶段不叫「同路比较」或省电评分 |
| 在哪一段发生变化？ | 轨迹、速度、电量、海拔采样 | 地图与主曲线共用选点；可打开另一张同时间轴小图，避免双轴。点读数、前后点按钮同样可用 |
| 当时的驾驶与环境怎样？ | 均速/最高速度、峰值功率、内外均温 | 图后分别成组，温度标明「全程均值」；不推断气温、空调或坡度导致了多少耗电 |
| 经常走的路有没有变化？ | 稳定路线分组、同向历史分布及有效样本 | 下一阶段：路线档案与同路线参照；地点同名或端点相近不能冒充相同实际路径 |
| 哪些过程值得进一步看？ | 功率/回收、温度/HVAC、地形、速度时长分布 | 后端补齐质量与聚合后，按专题下钻；胎压等技术信息留在按需展开层 |

不设「驾驶分数」「最省电司机」「节省了多少油费」等缺乏可验证模型的主指标。全车主毛电耗、补能与费用仍由概览/统计承接；不能给单趟分摊未建立归因规则的充电费用。

## 信息架构与三种原型

这是三种**行程信息结构**，不是重新选择已确认的湖畔主题。入口、结果/过程层级都在同一评审页切换，使用相同合成记录。

### A「出行回顾」——推荐

列表：**期间选择 → 里程为主的紧凑摘要 → 每日节奏 → 日期分组记录**。期间默认沿用近30日，另给近7日与自定义。摘要用次数/估算消耗作副读数，不再做一页与概览重复的仪表盘。节奏图只负责回答哪天开了车，点日进入当天记录；记录卡以起终点为识别锚点，距离为主数，时长/能量/电耗成一行有序副信息。首条也不额外预取详情或轨迹。

详情：**有地点和时间的标题 → 路线地图 → 距离/时长/能量 → 电量与电耗参照 → 过程曲线 → 驾驶与环境 → 原始明细/口径**。地图是记忆锚点，电量是车主最直接的结果；技术指标分组而非藏在一个总抽屉。默认速度图，可切电量/海拔，可选择上下对齐的电量对照图，选点在地图与图中保持一致。

取舍：比原列表多一个短摘要和一条节奏图，增加独立 stats 查询；收益是不用切进统计就能理解记录的时间背景。列表、摘要任一失败仍能使用另一部分。

### B「能耗透镜」——耗电优先

列表：**期间净电耗 → 每日电耗趋势 → 当前已载入记录的电耗横条 → 日期记录**。一眼比较眼前这些记录的数值，保留时间倒序；不把本页最高值叫全区间「最费电」。点条进入那一趟，参考线只来自单独请求的整体统计。

详情：**本次能量/电耗 → 电量区间与参考 → 对齐过程图 → 地图 → 环境**。支持从电耗的问题进入过程；未来补齐功率/回收、温度过程后更有解释力。现阶段只能看到共时变化，不能自动输出原因。

取舍：数据密度高，但地点记忆与找记录不如 A；建议吸收其中的能耗比较组件，不作为普通车主默认入口。

### C「路线足迹」——地点优先

列表：**本页起终点分布 → 有编号对应的路线记录 → 日期入口**。现有 API 模式只用已加载列表的端点，端点间虚线是关系示意，明确不是行车轨迹；不逐条请求序列。在能力预览中升级为稳定路线档案、常用目的地与完整区间空间聚合。

详情：**较大地图 → 起终点时间轴 → 结果 → 过程 → 更多指标**。未来可进入某条常走路线的历史、同向样本与不同日期，但长途旅程合并不与单次 drive 混为一谈。

取舍：回忆与发现最直观，地图占屏且依赖许可/坐标/网络条件；端点关系不等于同一实际路径。当前不适合为了地图逐条预取详情，路线档案需要新增契约。

## 指标覆盖、输入与交付顺序

「现有」表示冻结契约可提供，并不表示原型接通了服务或已获准实施。下表的「新增」都只是建议；移动端不直连 TeslaMate 表。

| 顺序 | 指标或功能 | 数据依据 | 展示与边界 |
| --- | --- | --- | --- |
| 1 | 时间、起终点、距离、时长、进行中 | 现有 drives | 保留；地点回退、日期/游标、未完成语义不变 |
| 1 | 单趟估算净能量 kWh | drives 已返回 | 新增到列表可见结果；原值为空不补0 |
| 1 | 单趟估算净电耗 Wh/km | drives/detail | 读数分级，与能量分开，不设好坏颜色阈值 |
| 1 | 期间次数、里程、能量、整体净电耗 | 现有 driving stats.totals | 单独请求，不从当前分页求和、不平均单趟比率；在长于730日的列表范围内摘要退化，不限制原列表 |
| 1 | 每日里程/电耗与日定位 | driving stats.buckets | 一条短节奏图，可切指标；点击日明确改变列表范围，不伪装原分页已包含当天全部记录 |
| 1 | 起止电量与百分点差 | detail.start/end.battery_level | 区间条；差值是明确展示的端点减法，不推导容量、续航或停车损耗 |

| 1 | 本次与个人历史参照 | 现有独立 stats 请求 | 参照为该行程开始日前30个完整本地日，所有路线；不包含本次，不复用列表区间或之后数据，不冒充同路线/同温度对照 |
| 1 | 平均/最高速度、最大功率 | detail | 保留 API 极值；均速包含整段行程时间，不从采样均值推算；最大功率不是回收能量 |

| 2 | 全区间地点搜索、距离/电耗筛选、排序 | **新增**列表查询语义 | 返回全查询匹配集与匹配集汇总；不在手机上筛20条却标成全区间搜索 |
| 2 | 驾驶总时长、单趟中位数、能量有效覆盖 | **新增** stats 字段 | 为期间摘要和比较提供真实分母；不能累加分页得到全量结论 |
| 2 | 常走路线、同向分布/中位数、可比样本 | **新增**稳定地点ID、路线分组与聚合 | 同向、距离容差、日期/温度等条件可见；先称「同起终点组」，无路径证据不称完全相同路线；样本不足不显示差异 |
| 2 | 全区间起终点/访问地图 | **新增**有界空间聚合 | 与当前「本页端点」区分，支持图到匹配记录下钻 |
| 3 | 功率正负过程、回收峰值、回收能量 | TeslaMate positions.power，**新增** series/聚合 | 正负围绕0；回收量由后端基于原始时间间隔与缺口规则计算，绝不积分200点采样或把负功率峰值当kWh |
| 3 | 累计爬升/下降、起止里程表 | TeslaMate drive.ascent/descent/start_km/end_km，**新增** detail | 用原始/服务端结果；200点海拔不能准确求累计爬升 |
| 3 | 额定/理想/估算续航起止及过程 | TeslaMate drive/position 的对应字段，**新增**契约 | 分别标口径，避免用SOC比例反推或宣称预测实际可达距离 |
| 3 | 速度区间时长与静止时长 | positions.speed/date，**新增**原始时序聚合 | 明确0、(0,40]、>40 km/h等边界和未覆盖时长；静止/低速不直接叫拥堵或高速公路 |
| 3 | 内外温度、设定温度、HVAC/加热状态 | TeslaMate positions，**新增** series | 共时上下图；开关状态不代表空调功耗，不输出气温造成的耗电占比 |
| 3 | 四轮胎压历史 | TeslaMate positions.tpms_*，**新增** series | 次级「车辆细节」专题；不用单点推断故障或驾驶评分 |
| 4 | 多段 drive＋途中充电的旅程回顾 | **新增**旅程实体/组合规则 | 更适合周末/长途；人工边界、途中充电、跨日与间断另行评审，本原型不冒充已实现 |

推荐先确认第1组及页面结构，再优先补第2组「找得到、比得对」。第3组增加深度，按用户反馈分期；第4组是独立产品问题。不要把所有缺口一起变成首版的前置条件，也不要因为当前API有限就永久放弃它们。

## 比较、缺失与可信度

1. 单趟净能量/电耗是续航差与车辆效率得到的估算，并非 Tesla 直接报告的电表计量；TeslaMate 的估算会随记录积累变化。当前 Mileaf 代码对非正续航差/缺少效率返回空，不擅自改成回收结果；UI仍保留收到的真实0或负值，不自行夹零。
2. 原型主例：32.6km、46分钟、5.22kWh、160Wh/km，SOC 76%→68%，端点差8个百分点。5.22/32.6×1000约160，四者不混称。参考154Wh/km来自独立合成统计，不称精确节省0.2kWh。
3. 全路线历史参考是背景，受到路线、气温、车速与估算覆盖影响。至少有正里程、有效非空电耗才显示读数；当前无覆盖字段，不做统计显著性、异常识别或驾驶优劣判断。未完成行程不显示最终差值/比较。
4. 同路线未来例：同向8次，净电耗中位数156Wh/km，范围142–181Wh/km。仅能力预览显示，所有数值为合成；模型、最低样本和质量口径需单独确认。它不是当前stats均值，也不是因果对照。
5. 空值显示「—」，0保留；全无记录保持空态，局部缺失保留已有结果。序列null断线，孤立有效点可见；不按固定时间阈值自称识别真实断采。地图缺失坐标不能连接跨点，地图失败不遮挡结果与曲线。
6. 地图仍受原有供应商许可、坐标核准与用户同意边界约束。原型使用自行绘制的合成路线示意；无外部瓦片、无真实位置、无GPS权限，不作为底图/坐标验收。
7. 期间stats只计已完成行程，列表可以有进行中；在摘要附近说明「已完成」，不因二者次数不同判断数据出错。归期按started_at，日图、日期选择和列表使用同一IANA日历区间。
8. 原型使用固定合成数据，不访问站点、数据库、配置、Tesla 凭据或外部地图；原型图表与查询动作只是交互演示，不代表正式Flutter/网络/真机验收。

## 原型评审与后续验收

原型入口与操作说明：[drives-expansion/README.md](../prototypes/drives-expansion/README.md)。同一页面用 `?variant=A|B|C` 分享；评审栏另有现有接口/能力预览、浅深色、100%/200%字号、数据缺失/无记录/进行中/旧快照/地图失败状态。手机产品区域以地点、数字和图形为主，工程能力标签放在评审区。

本轮验证：可见正文和浏览器渲染；三种结构切换；日期/图表读数到记录；列表点选与详情同步；电量/速度/海拔切换与地图选点；局部缺失/地图失败仍可阅读；360px与200%排版。原型不写模拟实现的单元测试，不运行未改动的Flutter测试/构建。检查记录见原型目录 `renders/verification.md`。

建议用户按三项观察评审：①10秒内找到具体一天的一趟；②详情前两屏说清里程、时长、耗电、到达电量；③看得出哪些是本次结果、个人历史背景与待建能力。上述是评审任务，还没有真人完成的成绩。

若后续确认实施，按第1组分成列表/详情/历史参考三个切片，沿既有App＋可控HTTP边界测试，补正式Flutter浅深/大字渲染，保持会话隔离、条件缓存、分页、独立恢复和性能边界。HTML通过不代替新展示验收；不提前关闭外部待验。
